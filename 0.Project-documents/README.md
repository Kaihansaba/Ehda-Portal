# Project Documents

## Project: Ehda Portal — Online Blood Donation Platform

### 1. Overview

This folder contains the main project documentation for Ehda Portal, an online blood donation platform developed as part of the Software Engineering course using the Scrum framework.

The documents define the project's purpose, requirements, team structure, responsibilities, and acceptance criteria. They provide a common reference for the development team and help ensure that the system is developed according to the agreed requirements.

### 2. Documents Included

This folder contains the following documents:

#### 2.1 Project Description

Describes the background, purpose, objectives, scope, target users, and main features of Ehda Portal. It explains how the platform aims to connect people seeking blood with potential donors and support communication about blood requests.

#### 2.2 Software Requirements Specification (SRS)

Defines the functional and non-functional requirements of the system, including account management, donor profiles, donor search, blood requests, notifications, messaging, donation history, and administrative functions. It also documents relevant constraints and privacy requirements.

#### 2.3 Roles and Responsibilities

Identifies the project team members, their assigned Scrum roles, and their responsibilities throughout the project.

The team consists of a Product Owner, a Scrum Master, and three Developers. The document explains how each member contributes to planning, development, coordination, testing, and delivery.

#### 2.4 Acceptance Criteria

Defines the conditions that user stories and system features must satisfy to be considered acceptable. Acceptance criteria help the team verify that implemented features meet the expected requirements and provide a basis for testing and review.

#### 2.5 User Stories

Defines the system's functional requirements from the perspective of its users. User stories describe what donors, blood seekers, and administrators need to accomplish through the Ehda Portal platform.

The user stories cover account registration and authentication, donor profile management, blood type and availability, donor search, location privacy, blood requests, notifications, request responses, messaging, donation history, and administrative functions.

Each user story includes a unique identifier and should be supported by clear acceptance criteria to help the development team understand the expected behavior and verify whether the requirement has been satisfied.

The user stories are used to develop and prioritize the product backlog, plan sprint work, guide implementation, and support product reviews and testing.


#### 2.6 Sprint 3–4 Requirements and Traceability (PDF)

- `Sprint-3-4-Requirements-FR1-FR15.pdf`: the blood request, notification, messaging and admin requirements (FR1–FR15, NFR1–NFR10) written for Sprints 3 and 4. They use their own numbering; the full, current list is FR-001 to FR-028 in the SRS.
- `Traceability-Matrix.pdf`: links those requirements to user stories #010–#020.

UML diagrams are in [9.Diagrams](../9.Diagrams/README.md).

### 3. Purpose of the Documentation

The project documents serve to:

- Establish a clear understanding of the project scope and objectives.
- Define system requirements and expected behavior.
- Clarify team roles and responsibilities.
- Establish measurable acceptance criteria for user stories.
- Support implementation, testing, and quality assurance.
- Maintain consistency between requirements, design diagrams, development tasks, and the final product.
